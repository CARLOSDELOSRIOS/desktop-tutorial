# Seguridad, transacciones y límites de garantía

La integridad declarativa (FK, CHECK, PK, UQ e índice filtrado) se aplica incluso a DML directo de usuarios autorizados para escribir. La vigencia cruzada de tarifas, los saldos, las transiciones y la no superposición de recursos se implementan en procedimientos. Para el rol `airline_operator` la base impide DML directo y solo concede las operaciones de negocio seleccionadas. Un dbo/sysadmin puede eludir procedimientos: se reconoce ese límite, se reservan sus credenciales para despliegue y se audita el estado con `10_audit.sql`.

Cada procedimiento inicia una transacción, solicita `sp_getapplock` exclusivo con propietario Transaction y usa XACT_ABORT, TRY/CATCH y THROW. El bloqueo `AirlinePAC:write` es compartido por convención entre todos los procedimientos y vive en el ámbito de la base de datos. Serializa comprobación y escritura, incluidos pagos y cancelaciones. El índice único de asiento activo es una segunda barrera independiente de la aplicación. Con bloqueo global no puede haber dos sesiones que lean simultáneamente la última plaza libre y ambas la consuman por esta API.

Se utiliza READ COMMITTED habitual para operaciones; el bloqueo de aplicación agrega serialización explícita de escrituras de la API, incluso si Azure utiliza READ_COMMITTED_SNAPSHOT. No se afirma que el nivel de aislamiento predeterminado por sí solo evite sobreventa. El análisis usa una transacción SERIALIZABLE y el mismo bloqueo para un conjunto coherente de consultas. Este diseño académico prioriza corrección y facilidad de demostración; no es una propuesta de alto tráfico.

Los procedimientos pueden anidarse en una transacción del llamador. Ante un error hacen ROLLBACK de toda la transacción activa; no implementan savepoints. El cliente debe tratarlo como fallo de la unidad de trabajo completa. El desplegador usa esto para revertir una instalación incompleta. Nunca se captura una excepción y se continúa afirmando éxito.

Las claves RequestKey únicas implementan reintentos idempotentes. Una repetición con igual clave y parámetros devuelve el mismo identificador; parámetros distintos se rechazan. Tras timeout, el cliente reutiliza la clave original, pues el resultado del commit puede ser desconocido. No se implementa reintento ciego que cambie la clave. En fallos 1205 o timeout se reintenta desde el principio solo después de verificar la unidad de trabajo y conservando la clave.

Las contraseñas se toman de variables o `.env` excluido de Git. El modo normal usa autenticación de Windows. Las entradas de negocio se envían con marcadores `?`. Los nombres de archivos SQL son una lista del proyecto, nunca identificadores SQL suministrados por el usuario. Los componentes de la cadena ODBC se delimitan y escapan con llaves; no se imprimen credenciales. Los mensajes de CLI son deliberadamente acotados; para diagnóstico técnico se conserva el tipo de excepción y el archivo/lote, sin cadenas de conexión.

Encrypt=yes es obligatorio. El valor seguro predeterminado es TrustServerCertificate=no. En Windows local, un certificado autofirmado puede requerir aceptar de forma consciente `-AcceptLocalSelfSigned`, que mantiene el cifrado pero omite verificar la identidad del certificado únicamente en desarrollo. Alternativa preferida: certificado emitido por una CA confiable y nombre coincidente. Azure obliga a TrustServerCertificate=no y FQDN de Azure. No se abre públicamente el servidor local ni se activa Browser/Agent.

Los datos son sintéticos y los correos usan `example.invalid`. No se almacenan documentos, números de tarjeta, CVV ni credenciales de clientes. No se afirma cumplimiento PCI DSS, FAA o de leyes de privacidad. Se concede lectura amplia solo por tratarse de un laboratorio sintético; un sistema real requiere vistas minimizadas, separación de funciones, retención, auditoría externa y gestión de identidad.
